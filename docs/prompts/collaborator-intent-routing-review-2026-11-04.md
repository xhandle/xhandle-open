# Review Collaborator intent, context selection and response behavior

Perform a detailed review of the current working implementation. Do not change application code or repair findings during this task. Write the findings, evidence and an implementation-ready design. Do not commit, push, publish, change provider preferences, invoke paid AI providers, or operate on customer workspaces. Diagnostic probes may use temporary files and disposable synthetic browser/Electron profiles.

Observed failure: a user asks “Whats the weather today?” in the Collaborator side panel while the Code architecture dashboard is visible. The app waits at “Retrieving the most relevant project and architecture context.” Earlier “what are we looking at?” also waited until stopped; “hey” answered. These are examples of an architectural routing problem, not requests for more hard-coded phrase exceptions.

Review the full submission-to-response path in both docked/full-page Collaborator, shared by Chrome and Electron:

1. Identify every eager context build, workspace indexing dependency, scope parser, attachment path, action/review preflight, planning request and fallback that can run before the request's evidence requirements are known.
2. Reproduce the screenshot behavior through the production App with a held workspace mutation lock and a local mocked provider. Measure whether a provider request starts before unrelated indexing completes. Check several prompts beyond “hey,” including weather, general questions, transformations of prior answers, and visible-screen questions. Do not credit mock text as proof of model answer quality.
3. Review how current view metadata, selected rows/nodes, attachments, thread history, pending decisions and explicit project constraints influence routing. Separate visible-screen orientation from a request to analyze a stored project's complete data. Check stale project focus, named records, ambiguous follow-ups and topic changes.
4. Check scope/coverage, current/history isolation, cancellation/thread switching, unsupported external/live information, prompt injection, and preservation of Collaborator's existing review and confirmed action workflows. Cite concrete defects and distinguish them from unverified risks.
5. Audit existing tests for implementation-shaped expectations and missing intent-level acceptance coverage. Run relevant existing regressions and targeted review probes; preserve application code unchanged and record verification limitations.
6. Propose a provider-neutral design that decides evidence needs before storage work. Consider direct conversation/general knowledge, thread-only transformation, lightweight current-view metadata, attachment-only reasoning, targeted workspace reads/reviews, confirmed actions, external tools, and clarification. These should be composable context requirements rather than another growing phrase whitelist.
7. Compare deterministic, model-based and hybrid routing, including the latency and ambiguity costs of an extra model classifier. Avoid a mandatory serial classifier for every simple message and avoid running destructive actions based on model classification alone. Define conservative fallbacks that do not automatically fetch the entire workspace.
8. Supply a fixed behavior/permission matrix and executable acceptance gates: no graph/index/read-planner calls for unrelated prompts under blocked/failed storage; no app data in unrelated prompts; useful screen orientation from bounded metadata; accurate targeted reads when needed; safe follow-ups/clarification; existing review/action confirmations; no fabricated live information; truthful progress; cancellation and thread isolation; model/provider neutrality; bounded memory and no large history parsing on direct routes.

Deliver a ranked review with source locations, reproduction artifacts, remaining questions, a proposed data flow and an implementation sequence. Recommend a suitable coding model based on current official guidance, distinguish the recommendation from the model running this conversation, and do not promise that a model choice alone guarantees correctness.
