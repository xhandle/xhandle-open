# Functional View: semantic STPA abstraction

The previous processor retained source-defined and cross-file calls regardless of their functional significance. Consolidation protected selected interaction kinds, but could absorb meaningful data/service flows. Derived hazard rows also inherited detailed-call exclusions. These policies confused source structure and interaction type with the functional abstraction boundary.

Functional model version 4 explicitly assesses each relationship as meaningful, implementation, or uncertain, with an evidence-grounded rationale. The prompt asks for control/feedback/decision semantics, independent of repository, language, API, filename, resolution, or interaction type. Only affirmative implementation assessments become internal operations. Missing assessments are uncertain; conflicting internal dispositions retain a reviewable connection. No row-count target is used.

Caller responsibilities are assessed separately. Consolidation cannot absorb meaningful or uncertain connections of any kind, or merge two independently meaningful/uncertain responsibilities. Implementation targets remain available to consolidation as supporting links. All original CBA rows and allocations remain intact; annotations are additive. No new view is introduced.

Each visible interaction retains its direct CBA rows first, followed by supporting implementation rows for its source and target responsibilities. Existing hazard and assurance trace consumers receive those trace IDs and evidence. Implementation-only derived rows are excluded from hazard expansion. Retained interactions are included unless an explicit analyst scope override excludes them. This does not reinterpret feedback or services as verified controller-issued control actions: interaction kind and inferred semantics remain in the analysis input.

The source inspector exposes each assessment and rationale. Older Functional models require regeneration; the versioned Functional layout storage avoids restoring an obsolete derived layout. Detailed architecture layouts are unaffected by this version change.

Validation uses deterministic response fixtures for classification/consolidation plus the real downstream hazard/assurance transformations. Fixtures cover same syntax with different significance, significant internal validation, data/service/feedback/control/unknown flows, implementation calls across source boundaries, missing assessments, protected responsibilities, exact source traceability, analyst overrides, ingestion parity, alternate filenames/extensions, cancellation, concurrency and unchanged raw rows. An isolated browser fixture checks persistence, stale-save rejection, source drill-through, Functional rendering, and detailed CSU containers. No customer data or paid model calls are used.

Limitation: semantic significance remains inferred by the configured model. These tests verify enforcement and data flow, not complete STPA correctness for an unseen codebase. Engineering review is still necessary, especially for uncertain relationships. Identical controlled responses produce identical mappings across ingestion paths; independent live model runs can still differ semantically.

Validation results: 29 regression suites / 223 tests passed. The isolated Chromium diagnostic passed with 22 detailed rows, 3 Functional nodes and 2 interactions, complete source coverage, persistence, navigation, local/Git rendering parity and retained CSU containers. Targeted ESLint and whitespace checks passed. Production build passed with repository warnings.
