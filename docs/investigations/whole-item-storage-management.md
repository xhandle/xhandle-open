# Whole-item storage management

Implemented in the shared web application. This investigation used source inspection, fake IndexedDB and synthetic data in nonpersistent Chrome contexts. The user's original 1,112 records, personal profile, installed desktop application and backup files were not inspected or cleaned. Existing authorized lifecycle changes were preserved. No commit, deployment, packaging or publication was performed.

## Schema findings

- Active project identities come from `xhandle.projects` and `xhandle.codeArchitectureProjects`. Durable removed snapshots live in workspace-graph `projects`, with `sourceStore`, `sourceData` and workspace ownership. Active metadata wins for display, but a conflicting persisted workspace owner must still block cleanup. Numeric/string aliases compare consistently; zero is valid. Project names and repository display labels never establish ownership.
- Architecture uses `xhandle/copilot_baseline`. `cba:<project>:<connection>` is the current rows root. `:metadata` is small publication metadata; `cbaMeta:<project>:<connection>` is the local metadata fallback. `:run` is the current provenance pointer and `:run:<fingerprint>` is immutable provenance, also referenced by surviving derived work. These pointers are not separate analyses. `:history:*` holds actual retained row snapshots. History has no independent restore UI, so Storage presents one grouped history item without a version count or restore promise.
- Architecture JSON trees use `{format:'xhandle-json-tree-v1',root}` descriptors and `:$part:` records. References can cross current/history boundaries. An unpublished ready checkpoint contains `rowRecord` and `runRecord` descriptors into those same immutable trees. Prefix matching alone is not a reclamation proof.
- `functional-decomposition-checkpoint:<scope>:<fingerprint>` is recoverable extraction/publication work. Publication stages immutable row/run trees, commits the result, metadata and run pointers together, and deletes its main checkpoint. It can retain a completed-but-conflicted ready checkpoint. Those checkpoints are protected.
- `<scope>:functional-work:<hash>` is an accepted request prompt/response cache, with a namespace incorporating scope, revision and model settings. These caches survive successful publication and are useful during interrupted resumes. They are neither analyses nor disposable merely because a current rows root exists.
- Requirement collections use assurance `artifactRows` roots `xhandle:cba-<kind>:<project>:<connection>`, with `chunkKeys` and separate pages carrying an explicit `parentKey`. There are local fallbacks and in-memory read/write caches. Valid page readers require the parent to agree. Requirement request caches also exist in `copilot_baseline` under `:requirements-work:<kind>:`; collection deletion preserves that reusable processing progress.
- Code hazards use `hazardAnalysisRuns`, small `runMetadata`, `hazardRunChunks`, `hazardRunStaging` and `generationCheckpoints`. Hazard pages and staging generations have distinct lifetimes; checkpoints and table caches may need them. The analysis repository identity (`repo.repoId`) can differ from the connection identity (`repo.id`). Storage follows the configured identity explicitly and refuses ambiguous multiple connections to the same hazard repository. Legacy shared JSON fallback data must not be silently imported or deleted during inventory.
- Workspace-graph artifacts/runs are additional saved representations, with exact `sourceStore`, `sourceKey`/`sourceId`, project and workspace identities. Removing the corresponding copies also removes incident graph relationships. Source-file representations are preserved.
- Older functional work also lives in the shared `xhandle.projectData` map, generic recovery checkpoints, project hazard heads/revisions, report stores/fallbacks and review evidence. App can reconstruct a missing safety report from the project map. Deleting only its report-store row would therefore be incorrect. Those older formats lack the complete small publication/write-ownership inventory needed for safe whole-item actions here. Recognizable project hazard/report roots are shown as **whole-item cleanup unavailable**, without hydrating their payloads. Other legacy/shared data stays inspectable in Advanced; no new destructive adapter guesses its ownership or completeness.

## Implemented UX and actions

The default view merges active registries and durable removed records. Saved items sit under their project, including removed projects that still own work. Hundreds of accepted requests and internal parts produce a small number of logical rows. Origin usage remains a browser estimate; per-analysis byte sizes and analysis counts are not invented. Dates appear only when publication or hazard metadata provides them.

| Item/action | Removes | Preserves / refuses |
| --- | --- | --- |
| Delete saved architecture analysis | Current rows, publication details, current run pointer, grouped row history, accepted functional request-cache roots, exact local rows/metadata fallbacks, and matching graph architecture edges/relationships | Project, connections, requirements, hazard evidence, independent reviews, immutable provenance needed by surviving work, external source files, layouts/source indexes, credentials and backups remain. Recoverable checkpoints, live analysis/saving and ownership conflicts refuse deletion. |
| Delete previous versions | Grouped architecture history roots and their graph copies; exclusively referenced parts when proven safe | Current result, current metadata/provenance and shared parts remain. No version restore is advertised. |
| Clean temporary data | Accepted functional request-cache roots and exclusively referenced parts | Requires committed complete publication metadata, complete selected-file coverage, zero failed/skipped files, no functional/storage error, matching immutable run identity/current pointer, and no recoverable checkpoint or active/pending work. Keeps final output, history, requirements processing progress, source indexes, credentials and backups. Confirmation explains additional future AI requests. |
| Delete requirement/artifact collection | Selected collection root, explicitly referenced pages whose `parentKey` agrees, other proven owned pages, local fallback and matching graph copies/relationships | Other collections and evidence, processing caches, project/connections, credentials and backups remain. Similar page keys without matching parent ownership remain. Generation and saving prevent cleanup. |
| Delete saved code hazard analyses | Saved result payloads and their metadata for one uniquely mapped repository, plus exact graph run/summary representations and incident relationships | Other repositories/projects remain. Uncertain/shared pages, staging and table caches are conservatively retained. Any generation checkpoint currently disables hazard cleanup; unsaved/running work, legacy fallback or ambiguous repository identities also refuse it. |
| Legacy project hazard/report rows | No whole-item delete is offered | Explicit unavailable state and inspection in Advanced; linked map/recovery/autosave data is preserved. |
| Restore / permanently delete removed project | Existing retained-project workflow | Normal sidebar removal stays recoverable. Permanent deletion retains its existing independent ID/workspace checks, write coordination, retained-row-last behavior, progress and persisted verification. |

Raw categories, individual-record tools and explicit credential selection remain behind initially collapsed **Advanced storage details**. The explanation says records may be parts of larger saved work. Collapsing Advanced clears its raw selections. Logical controls never consume raw selections. Unsupported or unassigned data is disclosed rather than attached by name or hidden as an empty project.

## Deletion, reference and state safety

`src/components/logicalStorageItems.js` owns inventory, identity checks, confirmations and cleanup adapters. Settings renders those results and actions; it does not implement fragment ownership. Inventory reads key cursors and small architecture/hazard metadata only, not architecture trees, request bodies, artifact pages, report markdown or hazard payloads. Legacy report inventory has a regression prohibiting payload reads.

Before cleanup, current registries and retained ownership are read again inside the graph mutation gate. Namespace overlap, numeric/string cross-workspace aliases, conflicting persisted workspace ownership and duplicated connection identities fail closed. A trustworthy saved timestamp is checked again before architecture mutation. Recovery/checkpoint presence and publication state are rechecked in the mutation transaction.

Architecture reclamation walks explicit references from both removed and surviving current/history/provenance/checkpoint roots, including descriptors nested inside ready checkpoints and encoded parts. Value requests are limited to 16 in flight. Only reached, owned parts absent from the surviving reference closure can be reclaimed. Missing/invalid references make reclamation conservative. If generic recovery roots exist, their uncertain external reachability causes parts to be retained. Abandoned, unreferenced parts are not purged just because their keys look related. Immutable run provenance is retained because surviving requirements/evidence may reference it. Hazard page reclamation is intentionally more conservative: payload/index deletion does not authorize deleting generations still potentially referenced by recovery or table caches.

New producer gates reject architecture, requirement and hazard saves during cleanup. Architecture generation and requirements derivation advertise their full work lifetime. Pending artifact edits are saved before deletion starts; failed or timed-out preparation starts no deletion. App invalidates the owned architecture snapshot with a clean empty publication, retires the hazard registry scope and synchronously clears the live hazard ref. Artifact cache versions advance and changed events reload mounted collection state. Existing project entries and repository configuration are not removed.

A persisted architecture deletion marker prevents App from rebuilding the deleted result from a legacy alias or independent review evidence. It is removed atomically by an intentional new save/publication or explicit replacement-row import. Export carries these markers, including retry state, so an exported deleted result does not revive from an exported legacy alias after import. Archive validation also accepts finite numeric IDs including zero, rejects normalized numeric/string duplicate destinations, and retains the original string-ID format behavior. A real archive round-trip regression exercises zero plus deletion/alias suppression.

Cleanup failures are not hidden by optimistic filtering. Architecture and artifact cleanup retain a discoverable pending marker until persisted verification and state reconciliation finish. Hazard metadata stays present until payload deletion and reconciliation finish, allowing retry if interrupted. Graph cleanup happens before canonical root removal; failure there leaves the canonical result discoverable. Stages are named and remain visible through the inventory refresh. Mutation exceptions abort the transaction and preserve their useful cause; the Chrome test rejects uncaught page errors.

New database opens have a 10-second bound, ownership reads a 10-second bound, graph mutation queue waits a 30-second bound, and transactions a 30-second abort timer. A late connection is closed; an expired queued cleanup cannot begin later. Timers and event observers are cleaned up. No startup purge or automatic retroactive cleanup was added.

## Material limitations

- This is not a universal legacy-data collector. Older functional map/recovery/report formats are inspect-only or explicitly unavailable for whole-item cleanup; they require more producer/state coordination before safe deletion can be offered. Traceability and other unsupported collections remain Advanced. No deletion adapter pretends that a raw row is an entire analysis.
- Hazard checkpoints currently block all hazard-group cleanup, including unrelated checkpoint scopes. Legacy hazard fallback also requires inspection instead of being parsed/hydrated merely to list it. Multiple connections sharing one analysis repository are deliberately unassigned rather than guessed.
- Immutable provenance, uncertain shared pages/caches, abandoned parts, independent review evidence and processing progress can remain. Deleting a result is not a promise to reclaim every byte previously associated with that repository. Browser origin usage includes unrelated caches and overhead.
- Coordination covers the current runtime and the existing graph mutation gate. It is not one cross-tab, cross-database transaction. Another writing tab or an explicit later backup restore can recreate data. Close other writing tabs before cleanup.
- Large legacy values may need inspection during an explicit deletion/reference proof. Request concurrency and transactions are bounded, but synchronous browser cloning/JSON work cannot be interrupted by a JavaScript timer. Inventory itself does not hydrate those values.
- Synthetic verification does not establish the ownership, completeness, recoverability or reclaimable size of the user's actual records, and does not update or verify an installed native application.
