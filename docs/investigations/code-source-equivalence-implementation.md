# Code-source equivalence implementation

Implemented against baseline `aa0666f8961acf6d0af09e88670fa6bee5033c8c` on 2026-10-05. This report accompanies `docs/codex-prompts/implement-code-source-equivalence.md`. Changes are in the working tree; no commit, push, live AI request, customer-source upload or user-browser-data mutation was performed.

## Delivered boundary

Local-folder and GitHub acquisition now share verified UTF-8 input handling and deterministic selection ordering. GitHub enumeration and every fallback read use one resolved commit. Selected bytes/text, context and non-secret settings have versioned run manifests. Truncated inventories, failed selected reads, malformed/truncated model output and failed persistence do not replace published architecture.

The deterministic evidence inventory is deliberately bounded: lexical Python single-line function/class definitions, unambiguous same-file direct calls and class membership. Canonical identities preserve exact file paths, qualified symbol case and relation kind; call sites and file text digests are separate occurrence evidence. Supported relationships are enumerated independently of model proposals and synthesized when omitted. Matching proposals can change prose without changing these identities or evidence-based eligibility.

This is **not complete functional-result convergence** for arbitrary repositories. Cross-file/import resolution, dynamic dispatch, multiline signatures, arbitrary data flow, other languages and semantic functional abstraction remain outside the deterministic inventory. Decorated, rebound, conditional-global and ambiguous call targets are conservatively excluded from verified calls. The lexical inventory is not a Python interpreter or exhaustive call graph. Unsupported model proposals remain explicit model-only/Needs Review records; model-generated prose, hierarchy and unsupported mappings can differ between runs. Existing source-language selection support was not removed.

The version-1 eligibility policy uses supported relation kind, source path and source symbol names. This is an eligibility heuristic, not proof of operational safety significance. Structural membership and test/example calls are excluded; supported operational/protective and consequential initialization calls can be included; uncertain executable consequences need review. New model-only records cannot revert to classification from presentation prose. Valid analyst overrides take priority. Stored legacy decisions retain their prior interpretation rather than being migrated on load.

Labeled fixtures: all four expected relationships represented (two executable Include, two structural Exclude), with zero missing supported mappings and zero blanket unresolved substitutions under controlled omission, duplication and wording changes. A second five-call fixture exercises initialization, feedback, protective validation, test code and uncertain utility code: three Include, one Exclude, one Needs Review. Unsupported model-only proposals are separately counted. These are synthetic fixture results, not coverage measurements for Alpamayo or another customer repository.

## Acquisition, run identity and failure behavior

- GitHub commit resolution fails explicitly; no silent main/master fallback. Recursive truncated trees fail before analysis. Entry mode/kind distinguishes files, symlinks and submodules; non-file entries are not analyzed as source or README content.
- Blob, Contents and raw fallback reads stay pinned. Blob digests are checked against the inventory. SHA-256 raw-byte and decoded-text digests are separate; fatal UTF-8 decoding matches local files. Existing local snapshot IDs remain readable. Local read-only/reconnect/FileList restrictions and existing file/chunk/time limits remain in place.
- One-file-at-a-time preflight hashing and ingestion avoid retaining all repository source texts. Selection ledgers distinguish analyzed, limit-skipped, not-selected and policy/entry-kind exclusions; adapter exclusions remain explicit. The old `fullCoverage` boolean was replaced by explicit bounded coverage metadata.
- Run fingerprints include verified inputs, versions, deterministic plan, requested settings and semantic context. Publication records actual response provider/model/effort. Comparison fingerprints omit informational adapter/folder names but retain contents, context and effective settings.
- Preference changes, missing provider/model provenance or inconsistent response settings stop publication. Existing provider selection is unchanged. Compatible checkpoints retain derived context and actual settings; incompatible checkpoints are not deleted. Unspecified provider/model settings prevent claiming compatible verified resume. Credentials do not enter manifests or hashes.
- Failed files retain resumable checkpoints and do not publish a partial result as complete. Successful rows, manifest/current pointer and checkpoint retirement publish in one transaction, with a concurrent-edit check. Cancellation/write/quota failure preserves the prior published state. UI state is updated after persistence succeeds.

## Storage, ownership and restoration

Existing stores are reused. Source evidence has immutable GitHub keys (`code:github:owner/repo:commit:path`) alongside the existing local snapshot namespace; legacy GitHub keys are still readable as legacy evidence. New staging does not clear the prior index.

Budgets: 350,000 bytes per ingested file; 32 MiB per architecture/history/checkpoint/import record; 128 MiB for checked source-index storage and 128 MiB for architecture history/checkpoints. Existing chunk/time limits remain. Browser storage estimates are advisory with a bounded wait; actual write failures are handled. Index budgeting tracks replacement sizes so identical snapshot keys do not accumulate duplicate files. Concurrent tabs can change available storage after an estimate; no estimate promises a successful write.

Published manifests belong to the project/repository scope and reference source snapshots. Checkpoints record the same scope, source descriptor and input manifest, identifying staged evidence retained for resume. Active/historical rows retain run fingerprints; prior published row sets are archived once per run fingerprint as a recovery copy. No automatic eviction of referenced evidence or old user history is introduced. Interrupted/incompatible checkpoint and source records are retained, not silently collected; explicit storage cleanup remains user-controlled. There is no new reference-aware cleanup UI. Capacity exhaustion stops the run rather than deleting history. Repeated different revisions therefore consume bounded remaining capacity until cleanup/export is performed.

In the isolated real-IndexedDB fixture, five repetitions of an identical publication retained exactly the same serialized record size: 255 characters before and after. A changed run retained the original manual edit/review in its recovery copy. Synthetic capacity, cancellation, concurrent-edit and injected quota failures preserved the active rows and run pointer. This small fixture measures redundant publication growth, not production repository capacity or peak heap usage.

Full project JSON now carries optional run records plus existing rows/analysis artifacts and embedded source excerpts. Import rebinds explicit copied ownership and metadata manifest paths while preserving saved IDs; rows and portable run records are committed together. Injected import quota failure rolls back both. **Full source-index files are not embedded in project JSON**; when the original index is unavailable, versioned remediation uses a retained excerpt with its original line offset or reports unavailable evidence. It does not substitute current source. Local access handles/permissions and credentials are not portable.

CSV remains an update/table format, not a complete project/evidence restore. Optional hazard trace provenance columns round-trip source revision and scope. Old files without those columns retain legacy behavior. Canonical history, manifests, review artifacts and full evidence restoration require the project JSON/backup workflow; CSV alone does not reconstruct them.
