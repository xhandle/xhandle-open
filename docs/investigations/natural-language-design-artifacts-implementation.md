# Natural Language Design engineering artifacts

Implemented November 7, 2026 from [the executable Codex prompt](../codex-prompts/implement-natural-language-design-artifacts.md) and [the implementation review](design-management-artifact-generation-review.md).

The feature is in **Design Management → Natural Language Design → Generate engineering artifact**. Reports and the SysML modeler remain unchanged. Existing manual design modules remain compatible.

## User workflow

1. Choose Concept of Operations, System Specification, Subsystem Specification, System Design Document, Subsystem Design Document or Interface Specification.
2. Explicitly choose the owning engineering project, destination design folder, system/subsystem or interface endpoints, and source modules and/or source notes. Legacy design folders are not silently treated as engineering projects.
3. Create the draft and generate it with the AI provider already configured in Settings. Each of the template's six sections is generated and checkpointed independently. Pause or leave the editor, then resume the saved draft; completed sections are reused.
4. Review the proposed document and its object changes. Accepting publishes a new working revision. It does not constitute engineering approval. Missing information is represented as unresolved objects.
5. Edit objects, their section, kind, text and supporting sources. Outline, Table, Document and Trace use the same canonical objects. Add objects, create named baselines, compare revisions, or export Word, PDF, Markdown and portable JSON.

Generated artifacts appear as typed modules in the existing folder tree, alongside legacy modules. The document presentation includes a cover, contents navigation, section hierarchy, unresolved-input highlighting, source citations and an evidence register. Artifact deletion removes its documents, drafts and baselines while preserving source modules. A folder containing artifacts cannot be removed until those artifacts are deleted.

## Maintenance and storage

- `artifactModel.js` supplies six versioned templates, scope validation, stable section/object identities, structured-response validation and manual-object preservation.
- `artifactSources.js` captures all selected source rows and their semantic fields, including hierarchy, content, attributes, links and provenance. It does not sample the first 80/120 rows. Known cross-project folder ownership is rejected. Unassigned legacy modules are included only through explicit selection.
- `artifactGeneration.js` uses the existing authenticated `/api/chat` routing, provider/model settings and cancellation signal. Responses must be bounded JSON with known object kinds, unique keys and exact source IDs. Unsupported content must be an unresolved gap. Requests time out after three minutes; retries are explicit through Resume.
- `artifactRepository.js` stores metadata, immutable revisions, section jobs and baselines in the named IndexedDB database `xhandle-design-artifacts`. Every store is indexed by engineering `projectId`; bodies never go into localStorage. Revision publication and proposal removal are atomic. Job tokens/versions and expected revision numbers prevent late or concurrent overwrites.
- Baselines reference immutable revisions. Portable JSON includes the current document, all exported revisions, source snapshots and baseline references. Word/PDF/Markdown are presentation exports of the current revision. Complete app backup/restore includes every artifact store and its indexes.
- `artifactMaintenance.js` runs at app startup even when Design Management is closed, on source/storage/focus/deletion events, and every 30 seconds as a fallback. Source changes mark a document stale; missing/corrupt evidence marks it unavailable. Maintenance never calls AI or rewrites accepted content.
- Regeneration produces a proposal. Changed source manifests or a changed base revision block acceptance and require a fresh proposal. Manually edited objects are preserved, including objects absent from a later AI response. Their original evidence snapshots remain attached; changed evidence produces a manual-review notice instead of silently replacing those citations.
- Tombstones and project deletion markers reject late generation writes. Existing permanent-project cleanup removes all four artifact stores for the deleted owner. Settings' storage inventory recognizes the new database.
- Opening blocked/unavailable artifact storage fails with a visible message and a ten-second timeout, closing any late connection.

## Explicit boundaries

Sources come from explicitly selected Natural Language Design modules and user notes. The coordinated systems engineering project workflow described below adds dependency-ordered document sets and generated artifacts as upstream inputs. Automatic adapters for hazard/code/System Test evidence remain future work. There is no automatic AI regeneration or engineering approval workflow.

Templates and source-ID validation cannot prove engineering correctness or standards compliance. Real-provider response quality was not evaluated in this synthetic test run. Inputs are limited to 30 modules and 350,000 serialized source characters; oversized selections fail explicitly. Responses are limited to 60 objects per section and 16,000 text characters per object, with a 2 MB accepted-document object budget. Broad source selections must be narrowed deliberately.

The artifact editor uses a section/object hierarchy with narrative, requirement, decision, gap and interface objects. It does not yet generate embedded diagrams. The follow-up restoration below adds the original requirements interactions, including hierarchy changes and rich-table editing. Trace retains the original requirements UI and supports artifact-to-source snapshots plus incoming/outgoing cross-document links for coordinated projects. Project ownership and document dependencies also have a project-level traceability view. This does not introduce a workspace-graph projection. Existing SysML generation continues to use its explicitly displayed legacy source module.

Artifacts have an owning project but do not introduce a new multi-user authorization model. Manual source assignments for legacy unowned folders rely on explicit user selection. Standalone artifacts and complete systems engineering projects can be moved between folders through the library; project members remain grouped with their owning project. Library ordering is separate from engineering generation dependencies. Engineering scope/source selection is fixed at creation; changed inputs within those selected modules are maintained, while a different scope/source selection requires a new artifact. Portable JSON is an export format; full application backup/restore is the supported restoration path.

Changes are local source changes. No commit, deployment or desktop application packaging was performed.
