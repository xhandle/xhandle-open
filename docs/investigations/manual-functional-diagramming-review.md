# Manual functional diagramming review

Reviewed commit `95fb4d3` by executing [this prompt](../codex-prompts/review-manual-functional-diagramming.md). Application code was not changed.

## Conclusion

The reported behavior is reproducible. Manual changes feed back into table-derived automatic grouping, which can create duplicate subsystems and move functions without an Auto arrange command. There are also ownership, undo, and persistence defects. This is more than a spacing preference: an operation on one function can change another function's subsystem in the functional decomposition.

The desired contract is direct manipulation: user-created containers keep their identity; deliberate placement and membership survive connection, rename, view changes, undo, and reload; unrelated elements stay in place. Imported/generated diagrams still receive their initial layout, and explicit Auto arrange remains available. This review uses that contract, rather than claiming feature-by-feature parity with external diagramming products.

## Findings, ranked

### 1. P1 — Newly created disconnected functions can disappear on reload

**Confirmed in Chrome and WebKit.** Start with two unallocated functions A and B, create an empty subsystem, select it, and click Add node. `n:new: 1` is visible. Wait over two seconds without editing or dragging it, then reload. The new function disappears. Its position was stored, but `:manual:v1` remained an empty array. The existing functions and subsystem survive.

The manual-node reconciliation effect updates `manualNodesStore` and schedules a 120 ms write via `persistManualSoon`. The cleanup effect depends on `manualNodesStore`; on that state change it cancels the pending new write and writes the old closure's value. The final new state is not immediately flushed by the newly installed effect. Further interaction can mask the defect by saving an earlier state.

Sources: [manual persistence scheduler](../../src/components/LiteSummaryDiagramReactFlow.js#L2915), [cleanup effect](../../src/components/LiteSummaryDiagramReactFlow.js#L3378), [manual-node reconciliation](../../src/components/LiteSummaryDiagramReactFlow.js#L4837).

**Correction:** persist the latest manual-node snapshot on state changes; use current refs for genuine unmount/project-switch flushing. Do not let cleanup for a prior state cancel or overwrite a newer queued write. Retain error handling and existing project-recovery integration.

### 2. P1 — Assigning one function changes another function's subsystem

**Confirmed in Chrome and WebKit for a top-level subsystem.** Fixture rows are Source/A → B and Destination/B → A. Create Group 3 and assign only A to it through the context menu. Both rows become `subsystem: Group 3`. B then moves into a generated Group 3; the original Source and Destination containers disappear.

`updateSubsystemForFunctionNodeIds` rewrites a row when either its source or receiver is selected. A row's subsystem is used as its **source function's** ownership by `buildSubsystemDiagramCategories`. Selecting A therefore also changes the ownership of B's outgoing row simply because A receives that interface.

Nested-system assignment uses `applySystemMembership`, which only updates source-function rows. In the nested browser case B correctly retained Destination. The two grouping paths implement different ownership semantics.

Sources: [incorrect endpoint condition](../../src/components/LiteSummaryDiagramReactFlow.js#L3160), [category ownership](../../src/App.js#L3404), [nested membership path](../../src/components/LiteSummaryDiagramReactFlow.js#L3699).

**Correction:** use a shared ownership update for top-level and nested membership. Change outgoing rows belonging to the selected function; preserve incoming rows' source allocations. Represent explicit ownership for receiver-only and disconnected functions in diagram state, rather than rewriting a different function's row to encode it.

### 3. P1 — Automatic reconciliation creates a second copy of a manual subsystem

**Confirmed in top-level Chrome/WebKit and system-nested Chrome cases.** Assignment into a manual Group 3 results in both a random-ID manual Group 3 and `g:auto:table:group-3`. The nested case likewise produces a duplicate Group 4 outside its system. Duplicates return after reload.

The App derives categories from functional rows on every relevant update. The diagram's missing-category check only includes boxes with `autoGenerated: true`. A matching manual subsystem is invisible to that check, so reconciliation treats it as absent. The later guard against layout when manual boxes exist comes after the duplicate-creation branch.

Sources: [category derivation effect](../../src/App.js#L8005), [generated-only identity sets and missing-category creation](../../src/components/LiteSummaryDiagramReactFlow.js#L3909), [late manual-box guard](../../src/components/LiteSummaryDiagramReactFlow.js#L3970).

**Correction:** reconcile categories against existing logical subsystem identities, including manual containers and their system ownership. Reuse the existing container; do not append a second ID for the same subsystem. Prefer stable identity over globally matching labels. Keep truly new table/import allocations supported.

### 4. P1 — Connecting a manual function erases explicit placement and can stack functions

**Confirmed in Chrome and WebKit.** In an unallocated A/B diagram, create Group 1, add `new: 1`, and explicitly assign it to Group 1. Connect it to A. The manual container remains, an automatic Group 1 appears, and both `new: 1` and A move into the automatic container at relative position **(18, 46)**. The resulting overlap persists after reload.

Before connection, the new function's saved placement has the manual parent and `groupingIntent: explicit`. `onConnect` replaces saved endpoint entries with only position and parent, losing `groupingIntent`. The structure builder promotes the function to row-backed provenance. `resolveGeneratedNodePlacement` then selects the inferred automatic group; `clampToGroup` clamps both old positions into the same corner. A gains inferred ownership from the new allocated source row because its own source rows have no allocation.

Sources: [connection writes](../../src/components/LiteSummaryDiagramReactFlow.js#L5000), [placement priority](../../src/components/functionalDiagramNodeReconciliation.js#L97), [clamping](../../src/components/LiteSummaryDiagramReactFlow.js#L1494), [row-backed structure rebuild](../../src/components/LiteSummaryDiagramReactFlow.js#L4601), [receiver ownership fallback](../../src/components/functionalDiagramNodeReconciliation.js#L44).

**Correction:** preserve endpoint placement metadata and explicit top-level placement during connection. Converting a manual function to a table-backed function must preserve its identity, hierarchy, position, and details. Creating an interface must not infer new ownership for an already deliberately placed endpoint. Avoid using clamping as a substitute for membership placement.

### 5. P2 — Undo/redo snapshots are overwritten by category reconciliation

**Confirmed in Chrome and WebKit.** Before assigning A, A and B each have relative position (60, 72) in their original groups. Undo restores their original row allocations but both end at (18, 46), with their groups regenerated. Redo's stored group set temporarily differs from the post-assignment set; reload recreates the missing duplicate. The nested Chrome case also moves the restored Source subsystem to a different location.

History restoration replaces nodes, groups, positions, and rows, but automatic category reconciliation can process restored groups against category metadata from another revision. `historyRestoringRef` guards checkpoint creation; the category/structure effects do not use it to make restoration atomic.

Sources: [history restore](../../src/components/LiteSummaryDiagramReactFlow.js#L3041), [category effect](../../src/components/LiteSummaryDiagramReactFlow.js#L3820), [structure rebuild](../../src/components/LiteSummaryDiagramReactFlow.js#L4496).

**Correction:** restore graph and matching row/category state as one consistent revision. Hold reconciliation until that revision is ready, and do not run inferred layout over restored user positions. One undo should restore one complete manual action, including parent IDs, geometry, and table ownership.

### 6. P2 — Creating or dropping a function inside a subsystem does not establish membership

**Confirmed in Chrome and WebKit; interaction gap rather than an exception.** Selecting a subsystem and clicking Add node creates a root node at a general canvas spawn point. Dragging that node visibly into the subsystem leaves `parentId: null`. The context menu does establish membership, but then exposes the defects above when table synchronization or connection occurs.

The toolbar handler ignores selected containers. Drag-stop explicitly preserves existing ownership; there is no drop-target membership operation. Dragging an existing child outward grows its old container instead of transferring it into another container. Top-level context-menu assignment clamps each function independently into the existing bounds before resizing, so multiple selected functions can also lose their relative arrangement; that multi-selection case is a source-level risk, not a separate browser reproduction here.

Sources: [Add node](../../src/components/LiteSummaryDiagramReactFlow.js#L4098), [assignment and clamping](../../src/components/LiteSummaryDiagramReactFlow.js#L3726), [child drag expansion](../../src/components/LiteSummaryDiagramReactFlow.js#L3570), [drag stop](../../src/components/LiteSummaryDiagramReactFlow.js#L5792).

**Correction:** add explicit, visible container targeting for creation and drag/drop. Choose the eligible intended container, convert absolute to parent-relative coordinates once, preserve spacing between selected nodes, and grow only the necessary bounds. Dragging within the same container should remain a presentation-only operation. Clearly define entering, transferring, and leaving a container; do not infer membership from incidental overlap during every render.

## Other code paths reviewed

- Subsystem rename calls the same ownership updater as top-level grouping, so findings 2 and 3 also apply to that path by inspection; a separate rename sequence was not browser-tested.
- System collision separation runs on group changes, drag completion, and resize completion. This deliberately can move another system when a container grows. It is a distinct policy from automatic category layout and reflects an earlier request to prevent system overlap. Preserve that constraint while defining predictable local collision handling; do not silently remove it as part of the fix.
- The initial-arrangement effect is already gated by a persisted pending/complete marker. The confirmed assignment/connection failures do **not** require clicking Auto arrange or re-running that initial effect. Disabling initial arrangement would leave the core defects unresolved.
- The App's empty-project flow presents a wizard; Skip Wizard creates starter Node 1/Node 2 rows. The functional workspace is gated by `responseRows.length > 0`. A truly empty manual canvas therefore also needs a deliberate product decision. Tests here used two starter-style unallocated functions, not a new-project wizard run.
- Existing rename, edge update, deletion, resizing, and parent reconciliation were read. No claim is made that every possible sequence is covered by the browser scenarios.

## Implementation plan

1. Fix manual-node persistence first, with a create → idle → reload regression.
2. Centralize manual membership updates. Keep explicit node/container identity and ownership as the authority for that action, then derive compatible source-row allocations. Share the implementation across top-level, nested, rename, and ungroup operations.
3. Make category reconciliation reuse manual containers and preserve explicit placement. Keep manual-to-row-backed conversion lossless when an edge is created. Apply table/import-driven membership only to the intended changes.
4. Make history restoration atomic with derived category state and persistence. Verify undo/redo before introducing new drag/drop semantics.
5. Add selected-container creation and drop-target membership with feedback. Preserve absolute placement and multi-selection offsets; do not rearrange unrelated siblings or groups.
6. Retain initial layout for imported/generated graphs and explicit Auto arrange. Keep routine manual operations separate from those layout entry points. Preserve existing system containment, collision, cursor, resize, search, and performance behavior.

Avoid solving this with repeated Auto arrange, arbitrary delays, globally disabling grouping, or replacing all saved positions. Those approaches would conceal incorrect ownership and sacrifice existing capabilities.

## Required regression acceptance criteria

- Create a subsystem and add several functions: exactly one subsystem, intended parent IDs, no unexpected movement of existing elements.
- Select a subsystem or system and add a function; drag functions in, out, and between eligible containers; test nested and top-level cases plus multiple selected functions.
- Group A when A and B communicate in both directions: B's source allocation and geometry remain unchanged.
- Connect a manually assigned function: retain its manual container and position; preserve the other endpoint's explicit placement; create only the interface row.
- Rename function/subsystem/system: preserve container identity, connections, ownership, descriptions, and geometry; reject actual identity conflicts without creating duplicates.
- Save disconnected functions and notes through idle, reload, project switch, and diagram/table/split-view transitions.
- Undo/redo add, connect, assign, ungroup, rename, resize, and delete: exact restoration of rows, graph identity, hierarchy, geometry, and persistence.
- Mixed imported/manual diagrams and repeated CSV replacement retain intended behavior; initial imported/generated layout still matches Auto arrange, saved diagrams reopen as left, and deliberate Auto arrange still works.
- Large graph editing does not add whole-graph layout work to pointer moves, selection, or typing.

## Execution and evidence

- Seven completed isolated browser runs: Chrome mixed, nested, manual connection, and disconnected reload; WebKit mixed, manual connection, and disconnected reload. No page exceptions in those completed runs. These are behavioral defects despite the absence of runtime errors.
- Existing focused suites: **5 suites, 51 tests passed** (system integration, history serialization, node reconciliation, system groups, initialization). Their current coverage does not catch these App/category/persistence interactions.
- [Raw measurements](manual-functional-diagramming-measurements.json) contain synthetic rows, saved positions/parents/groups, and rendered transforms at each step. Stored and rendered state are both retained because their divergence is itself relevant.

Configure `XHANDLE_PLAYWRIGHT_PATH` and, for Chrome, `XHANDLE_CHROME_PATH` as in the script header. The script records observations; it is an investigation tool, not a passing correctness assertion for the defects.
- Automated WebKit is not the user's installed Safari and extensions. No native Windows run, live customer project mutation, production changes, commit, or push was performed.
