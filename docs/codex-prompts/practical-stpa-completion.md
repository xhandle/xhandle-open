# Practical STPA completion and stopping rule

Implement this prompt against the active code-based STPA workflow. Preserve unrelated working-tree changes. Use anonymous synthetic fixtures only. Never put private workspaces, organizational profiles, incident diagnostics or credentials in tracked source. Keep native code in the private desktop repository. Do not commit, publish or release.

## Product requirement

Assessment-level shortcomings must not leave a run incomplete or in an assessment-failure state. Complete ordinary AI-generated assessment rows using the best available engineering judgment. Users review the results. Source substantiation, exhaustive supporting evidence and perfect wording are not completion prerequisites.

Do not replace assessments with special evidence-gap conclusions, add mandatory caveat prose, add qualification banners, or append boilerplate limitations to ordinary fields. Preserve normal user-authored and model-generated assumptions. Do not fabricate supporting source quotations, executed verification results or a claim that the system has been verified safe.

## Acceptance and stopping rule

- Define the practical minimum bar explicitly: correct row/action identity, an applicability decision and rationale, populated core UCA/loss/hazard/scenario fields, classification, system constraint, software requirement and verification proposal. Prompt for coherent reasoning in the stated operating context.
- Preserve analyst decisions, original evidence and unrelated edits.
- Accept usable drafts immediately. Do not reject them for terminology, unavailable citations, missing extra context or requests for more exhaustive analysis.
- Use a small fixed refinement budget. Retain accepted rows and reuse their checkpoints; do not repeatedly revise them for hypothetical improvement.
- For evidence questions or unusable model output, attempt bounded targeted finalization of the unresolved rows. If model output still cannot populate a row, produce a normal action-specific best-effort draft. Do not assume generic protective roles or fatal consequences. Record recovery provenance internally without substituting failure text for the assessment.
- Make optional deeper semantic review a user-invoked activity rather than a mandatory completion gate in this workflow.
- Preserve HARA/FHA behavior and legacy internal strict-mode compatibility. Cancellation, credentials/account rejection, programming faults and storage-integrity problems are operational interruptions; do not disguise those as successful provider requests.
- Preserve ordinary CSV, storage, requirement derivation and user-edit behavior. Do not introduce a new result schema or completion disclaimer into the UI.

## Validation

Add synthetic regressions for completion despite missing substantiation, bounded unusable-output repair, ordinary final rows, accepted-row reuse, preserved analyst decisions, citation provenance, cancellation and account errors. Cover the real runner, CSV/save/reload and downstream consumers. Run the offline STPA harness, relevant regression suites, lint and a production renderer build. Make no paid model calls. Report what passed and any unverified behavior honestly.
