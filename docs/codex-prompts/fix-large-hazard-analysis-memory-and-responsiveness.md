# Fix large hazard-analysis memory usage and GUI responsiveness

Implement and verify the fixes that block the next xHandle Desktop release. Preserve the existing working tree and customer data. Keep shared application changes in xhandle-open and native changes in the private desktop repository. Do not commit, push, change release versions, or publish an update as part of this task.

Start from the reproduced production Electron failure documented in `docs/testing/pre-release-readiness-2026-11-16.md` and `/private/tmp/xhandle-precommit-large-hara-20261116/`: 1,500 interfaces × three operational contexts × seven guide phrases (31,500 assessment rows), near-complete Projects HARA classification, five-second input timeouts, and a native V8 JavaScript OOM. The standard 17-suite gate passed, so retain a separate large-project acceptance gate.

1. Inspect native crash/flight evidence and profile the production workflow in real time. Identify the allocations and main-thread tasks responsible for growth and stalls. Measure phase duration, retained/peak memory, publication/checkpoint payload size, renderer timer gaps and actual input handling. Distinguish application work from test harness overhead; do not guess the cause from the heap-limit message.
2. Remove unbounded or quadratic workbook construction, duplicate snapshots, expanding provenance/goal lists, repeated serialization/hash passes and excessive publications. Use bounded batches, incremental indexes/storage and worker execution where supported by evidence. Keep the renderer responsive through generation, final consolidation, durable save and reload.
3. Preserve every assessment and its exact source identity, canonical links, classification reasoning, safety-goal membership, organizational guidance, manual decisions, cancellation and resumable checkpoints. Do not fix memory by silently dropping rows/evidence, shortening substantive outputs, skipping validation, weakening responsiveness thresholds, adding synthetic results, or merely increasing the heap limit. Keep semantic validation strict.
4. Add focused regression tests for the diagnosed causes and bounded growth. Exercise STPA and HARA in both Projects and Code-Based Architecture with real production dispatchers and isolated Electron storage. Include output-limit/malformed/missing-row/rate-limit recovery and cancel/reload/resume.
5. Run the 31,500-row cases sequentially, with no overlapping performance workloads. Require completion, exact identities/counts, valid HARA fields/ASIL and goal links, durable save/reload, no silent fallback, no renderer crash, no input timeout, and the existing maximum two-second renderer-gap gate. Record memory and CPU evidence. Check a representative larger or repeated workload if needed to detect retained growth; use evidence to avoid unnecessary repeat runs.
6. Run the full Electron regression gate on the final source, changed-source lint and whitespace checks. Preserve failed evidence and report exact results, source fingerprints, measured limits and remaining release work. Update the readiness report only when the large gates actually pass. Controlled-provider success does not certify arbitrary model-output quality or Windows/Linux installers.

Deliver the code fix, reproducible diagnostic/tests, and a concise verification report. Continue until the reproduced crash and large-analysis responsiveness failures are resolved and final verification is complete, or a concrete external blocker prevents further work.
