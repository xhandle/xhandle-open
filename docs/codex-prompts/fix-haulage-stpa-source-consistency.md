Observed baseline: a synthetic teleoperated haulage fixture produced 105 STPA rows. Its 68 applicable assessments covered useful failure themes but contained conflicting requirements, invalid tests, incorrect arithmetic and profile-driven scope drift. Treat this as a general pipeline defect, not an invitation to hardcode this fixture's answers.

Required work:

1. Follow evidence through import, functional abstraction, hazard input preparation, applicability, generation and publication. Preserve original source file content, function ranges, source identity and supplied interface/lifecycle metadata. Functional summaries must not replace implementation evidence with file-name-only placeholders.
2. Separate user/project operating concepts from organization guidance during context generation. Carry source descriptions and project analysis context, not just function labels. Explicit project authority/mode and implementation facts take precedence over profile examples. Never silently rewrite saved contexts or force every remotely supervised system into teleoperation.
3. Strengthen STPA applicability reasoning. Gates and validation decisions can govern motion; their false acceptance or unsafe provision cannot be excluded solely because the action is a gate or has downstream effects. Distinguish ordinary sequential prerequisites, hypothetical reordering, and actual concurrency. Check each phrase independently, preserving analyst decisions. Unsupported automatic exclusions should request focused evidence rather than becoming unexamined final answers.
4. Ground requirements and verification in the same source-defined facts. Preserve explicit reset, reset-cycle motion inhibition, stop retention, brake-mode priority and invalid-input stop-output behavior when these appear in evidence. State proposed behavioral changes explicitly with their safety justification; do not call them existing safeguards or silently weaken existing safeguards to improve availability. Do not prohibit protective brake selection because motion inputs are invalid.
5. Keep numeric constants, equality, units and calculations consistent across scenarios, requirements and tests. Use source facts when supplied. Introduce new limits only as proposed values requiring validation. Distinguish scheduler period, command-response deadline, brake acknowledgement and physical stopping time. Use bounded local arithmetic checks for explicitly supported expressions where practical; never execute supplied source code or arbitrary expressions.
6. Distinguish a hypothetical failure of an existing safeguard from a demonstrated source defect. Keep causation qualified in visible fields. Verification must have a consistent stimulus and expected result, including prerequisite state, current timestamps, command sequence and explicit reset. Do not mistake ordinary safe early rejection for incomplete validation.
7. Add focused regressions for actual observed failures: same-cycle motion on reset, automatic restart without reset, collision/estop emergency-brake expectations, 0.2 s telemetry versus 0.3 s command lease, continued protective output on invalid telemetry, replay rejection despite command freshness, and incorrect stopping-envelope arithmetic. Include negative controls for different systems, explicitly proposed changes and legitimate hypothetical faults. Preserve HARA/FHA behavior, checkpoint identity, cancellation, targeted retry and quick-run performance. Avoid a mandatory additional model pass for every row.
8. Invalidate stale automatic generation/screening checkpoints when their acceptance contract changes. Preserve analyst inputs and existing completed results; require fresh regeneration to evaluate the new behavior.
9. Run focused tests, the offline STPA harness and the production build. Write an investigation note with concrete changes, results and limits. Offline provider doubles prove pipeline behavior, not live narrative correctness; do not claim all semantic errors can be proved absent by string checks.
