# Replace Projects HARA post-processing with review, correction and verification

Replace the current combined review/editor and retry loop with a bounded workflow modeled on a careful spreadsheet review:

1. Inspect the complete saved table, its structure, shared Item, operational contexts, related rows, classifications and goal relationships. Identify explicit issues before editing. Include deterministic inspection and an AI issue-finding pass covering all applicable rows with shared table context.
2. Make one targeted correction pass against those findings. Every proposal must identify its source row and the finding it addresses. Keep sound cells, generic source losses/hazards, STPA evidence, identities, applicability, Item boundaries and analyst-owned cells intact.
3. Independently verify proposed changes against the original assessment, source/context, related rows and the HARA reasoning rules. Check engineering reasoning and regressions as well as schema and arithmetic. Use a fresh verification request with no authority assigned to the editor's rationale. Keep independently sound changes when an unrelated correction is rejected.

Use the primary analysis's practical acceptance bar throughout. All assessments remain final. Retain the existing final decision when no sound improvement is available. No new acceptance gates, blocked assessments, Needs Review labels, status columns or indefinite repair loops. Cancellation, account and storage errors remain visible without converting saved final primary results into failed assessments.

Require correct reasoning about people avoiding harm. Do not treat a proposed requirement as an implemented capability or lower controllability/severity by crediting the internal protective behavior being assessed. Preserve legitimate C0/C1 decisions. Correct blanket rules that prohibit a still-required emergency stopping response, while preserving legitimate stale-command validation. Potential Harm should describe injuries to people, independently of intentionally generic source Loss/Hazard fields. Distinguish fault-to-hazard FTTI from monitoring periods, warning windows and response deadlines. Check timing dimensions and start/end events. Express functional goals and consistent, testable requirements without inventing implemented safeguards. Technical descriptions such as "incomplete gear engagement" are valid failure descriptions, not incomplete-assessment labels.

Preserve durable caches with phase-specific inputs, bounded concurrency, progress, saved originals, row hashes, undo history, draft synchronization, CSV/workbook exports and deterministic event/goal ASIL recalculation. Verify shared-goal refinements before applying them to linked events. Do not bundle private Codex runtime packages or private skills into the public application. Implement the equivalent review instructions and data inspection within the shared application code.

Use anonymous synthetic fixtures in public source. Test the known failure patterns, regressions, independent verification, partial rollback, protected cells, stale/ambiguous IDs, evidence references, bounded requests, caching, cancellation, storage errors, goal propagation, export/reload/undo, and final-result status. Preserve all unrelated edits.

Run relevant regression tests and a production build, then validate the exact renderer in isolated Electron. Where separately authorized, validate a representative private CSV with the configured provider, keeping inputs/results outside tracked source and preserving the original file and live project. Compare outputs and report observed improvements and remaining problems honestly; do not promise a score in advance. Update the live preview only when idle and after saving a private recovery backup.
