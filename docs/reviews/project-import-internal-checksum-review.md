# Project import and internal checksum review

Reviewed 2026-10-29 in `/Users/Nick/xhandle-open`, Node 20.20.2. Review only: no runtime implementation, archive version, default export behavior or stored checksum was changed.

## Findings, ordered by impact

1. **High compatibility risk: replacing the archive hasher without versioning rejects valid existing large archives.** `src/features/code-architecture-transfer/projectArchive.js:189,200,306,356,390` writes and verifies the same hash.js digest over the uncompressed line stream. At **536,870,912 hashed bytes (512 MiB)** it ceases to be standard SHA-256. A fresh production-parser test validated a 545,941,898-byte synthetic body with its legacy digest, then rejected the identical body carrying independent Node SHA-256. A corrected-only reader would conversely reject that legacy footer. This is a demonstrated format interoperability defect, **not a demonstrated current import failure**. Current writer/current reader agree; changing only the implementation is breaking even if the file still says version 3.
2. **Medium, scale dependent: persisted hazard aggregate/index checksums have implicit legacy semantics.** `hazardRunChunks.js:10,21–35,145–200`, `hazardChunkIntegrity.js:13–27`, `hazardTableIndex.js:4,50–59`, `hazardRowIndex.js:7,43–50` have no algorithm field. Normal page hashes are far below the boundary; aggregate input is only 65 bytes per page. A single run needs **8,259,553 pages** before its aggregate crosses the boundary. Table/row index JSON is unbounded metadata and can grow independently. Changing readers alone can reject sufficiently large old descriptors, cause index rebuilding, or block full hydration/export/row deletion. No such customer descriptor or failure was reproduced. Ordinary bounded pages and ordinary indexes give identical standard/legacy hashes.
3. **Medium migration design risk: a new hazard format string alone is not a safe older-reader gate.** `hazardRunChunks.js:7–8,17,124` recognizes only the exact v1 marker; an unrecognized marker can be treated as an ordinary unchunked run rather than explicitly rejected. New authoritative storage formats need a database-version/capability gate as well as a new descriptor contract. Hazard DB version is currently 5 (`hazardSchema.js:3`); archive versions 1/2/3 are accepted explicitly and other archive versions fail (`projectArchive.js:387`). Do not depend on an ignored new algorithm property or unknown payload marker to stop older clients.

**Is importing affected today, and what breaks if we change the checksum implementation?** The defect exists in import's archive-validation primitive today, but matching existing exporter/importer implementations still validate matching large archives. There is no evidence that this defect alone prevents importing the customer's project. A standard-only footer reader breaks large legacy archives; a standard-only footer writer breaks current readers. Changing only the transient comparison digest does not change an on-disk contract. Changing a bounded page implementation normally changes nothing; changing persisted aggregates/indexes requires versioned readers/writers and coordinated desktop/browser rollout. Corruption rejection still works under the current legacy algorithm: being nonstandard does not remove all integrity protection. These checks are unkeyed integrity checks, not authentication against someone able to rewrite the checksums.

`readArchiveLines` slices raw files at 256 KiB and uses streaming TextDecoder. For gzip it detects 1f8b magic, streams DecompressionStream('gzip'), then splits on LF. The archive checksum is technically over decoded text re-encoded by hash.js, not arbitrary original file bytes: TextDecoder's default is nonfatal and handles initial BOM. Ordinary exporter output is valid BOM-free UTF-8; fresh Unicode/escaping checks establish its byte-for-byte agreement with Node. CRLF is not normalized: replacing LF with CRLF without recomputing checksum is rejected. Gzip CRC/truncation and the upload checksum are additional layers, not algorithm markers for internal digests.

`projectHazardExport.js:36–78` validates existing chunked runs, omits architectureRowsSnapshot, repages into a fresh generation and recomputes aggregate. It does not simply copy every source descriptor/index. Import prepares new derived indexes after validation. Thus a future versioned archive can adopt a new portable representation without silently mutating the source run; source-reader compatibility still must be retained. A raw dataset byte count is not necessarily serialized-token bytes (escaping, UTF-8, numeric arrays and compact framing differ).

## Bounds and scale

Installed `hash.js/lib/hash/common.js:64–77` uses `len <<= 3` and zero high length words. At 512 MiB the encoded bit length wraps; each update still processes the real message blocks. This explains both mismatch with Node and continued meaningful corruption detection. `sha.js/hash.js:80–94` writes numeric high/low length words instead.

For ordinary hazard production tokens, an 8192-unit text token expands at most roughly 49 KiB in JSON escaping, a binary token has at most 8192 byte numbers (~32 KiB), and a page flush occurs after a token pushes the accumulator past 16 Ki units. Array commas/outer brackets add small overhead (many short tokens can add a few KiB). There is no path where a normal 10 GiB hazard run is hashed as one 10 GiB page. Arbitrary tokenSource callers or hand-built archive values are not governed by all these normal producer bounds; validators do not enforce a hard page-byte ceiling. A review should not label that an established large-page failure.

Aggregate boundary: ceil(536870912 / 65) = **8,259,553 pages**, hashing 536,870,945 bytes. At nominal 16 KiB token pages that is about **126.03 GiB** of token serialization per run (actual byte scale varies with Unicode/escaping, page overshoot and partially filled last page). A nominal 10 GiB token stream is about 655,360 pages and **40.625 MiB** of aggregate hash input. Decimal 10 GB is smaller still. Summing many runs can exceed 512 MiB of archive bytes long before any per-run aggregate does.

Indexes must be assessed separately. A representative table page object with seven-digit sequence, one range and digest is 115 ASCII bytes, plus its array comma. Roughly 4.6 million such retained pages yield 512 MiB of index JSON (about 71 GiB at nominal page scale); more ranges lower that count. Row spans cost their JSON coordinate lengths plus comma: representative `[8259552,0,8259552,100]` is 23 bytes plus comma, about 22.4 million spans for 512 MiB before other metadata. These are examples, not enforced limits or estimates of customer data. Runtime maximum string/heap limits may prevent constructing an ASCII JSON index that large first (in particular V8 strings near 512 MiB); Unicode metadata and other engines differ. Index size/latency is a separate latent scaling risk, not proof all hazard checks already hit the padding boundary.

JSON tree normal size is also not total dataset size: even a page with 64 inline maximum-length strings is roughly 12 MiB at worst JSON escaping; recursive pages bound child counts. Large key names and reference prefixes mean no unconditional global node-byte invariant should be asserted. Standard WebCrypto writer versus legacy transfer validator is a latent mismatch if an actually produced individual node crossed the threshold, unlike matching hazard page writer/reader. No such node was demonstrated.

## Smallest compatibility-safe sequence (proposed, not implemented)

1. **Keep the upload fix separate and deliver it through normal release verification.** Correct sha.js uploaded-byte digest matches the server's existing Node contract. It does not reinterpret archives or saved hazard data. The reported message is thrown by server upload finish, whereas internal footer failure says “Project archive checksum failed.” This source-level distinction supports the immediate fix without claiming a customer replay. Historical-run selection/export speed amplifies byte counts and time, but is separate scope; no retention redesign here.
2. **Specify the contracts and introduce readers before new writers.** A new archive version (e.g. v4) must declare standard SHA-256 and exact UTF-8/framing rules; validate version/algorithm before commit. Versions 1–3 retain explicit, frozen legacy validation. Unknown versions/algorithms fail closed. A successful legacy check is required for old data; no generic digest-mismatch allowance. Add standard new-version exporter only after those readers exist. Preserve export/retention of older archives rather than deleting/re-signing backups.
3. **Separate archive footer migration from authoritative hazard storage migration.** Minimal first release can version only the archive footer while retaining explicitly legacy hazard-v1 payloads. Bounded page and JSON-tree checks need no broad replacement. If new archive export regenerates hazard descriptors, its version must unambiguously specify their algorithm/format too. A v4 standard footer alone does not imply a copied nested aggregate is standard. Transient comparison hashing can be changed independently if wanted; checkpoint namespaces/provenance should remain stable.
4. **For actual stored aggregate/index migration, use a database gate plus new descriptor/index contract.** Keep read support for old hazard v1/index v1/v2 semantics. New writes use an explicit correct algorithm contract. Older clients opening a newer shared DB must refuse by supported DB version rather than mistake new descriptors for inline runs. Coordinate desktop bundled UI and browser UI capabilities; version discovery/capabilities are more reliable than assuming a server update changed every client. Old clients must either receive a deliberately supported legacy export from the new app or reject the new archive cleanly. Do not emit disguised v3 standard files to satisfy old apps.
5. **Migrate only after validating the original source, with staged publication.** Reuse the generation/lease mechanism conceptually: stream validated old pages into a new generation, recompute new aggregate/derived indexes, verify count/ownership/token structure, compare source storageRevision/generation at publication, then atomically switch root+metadata. On abort, quota failure, competing save or shutdown, original remains authoritative and new staging is reclaimable. Preserve original archive backups and all historical runs; no silent history omission. Old data stays immutable unless successfully migrated. Index-only rebuild must not rewrite payload digest to mask source failure. Review rollback for pre-existing roots/indexes separately before shipping migration; current import journals are not a ready-made multi-version migration transaction.
6. **Avoid permanent double hashing.** Version-dispatched readers hash once using the specified algorithm; they do not need both. For an explicitly supported ambiguous transitional format, computing both costs two compression-function passes per validation and two states, not twice the retained dataset memory. Current importer already scans twice, and destination-conflict comparisons can hash whole values again. Dual footer checking on both passes can approximately double checksum CPU; benchmark real devices before proposing it. Re-reading for fallback also doubles I/O/decompression; parallel incremental dual states avoid that I/O but not CPU. There is no measured dual-validation performance result here and no need to introduce dual acceptance for current unambiguous version policy.
